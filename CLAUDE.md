# Preferences across repositories

- **Change files with the Edit or Write tool,** not with Python, sed or other scripts run through the shell, so the exact diff is visible. Several small changes in one file are several Edit calls. Scripts are fine for reading and checking files.
- **No auto memory** (it's turned off in `~/.claude/settings.json`). Anything worth keeping for later sessions goes in a CLAUDE.md instead: the repository's `CLAUDE.md` for rules about that project, or this file for preferences across repositories. Propose the line and where it goes, and add it once agreed. A repository change goes through that repository's usual commit and PR process.
- **Ask before every change to my own Claude Code setup,** even one I asked for: this file, `settings.json`, `keybindings.json`, `scripts/`, `skills/`, `commands/` and `agents/` under `~/.claude/` (what its `.gitignore` tracks), `~/.claude.json`, and any repository's `.claude/settings.json` and `.claude/settings.local.json`. They're versioned only in a local git repository or not at all, without review; a repository's `settings.json` takes effect in the checkout before its PR is reviewed; and `settings.json` lets `scripts/` run without a prompt. Show the exact change first. Ask rules in `settings.json` make Claude Code prompt for each edit, in every mode. Scratchpad files, worktrees and plan files are left out on purpose and need no question.
- **Collect suggestions, then ask about them together.** A suggestion outside the current task, such as a change to my setup above, a line for a CLAUDE.md or a follow-up PR, goes into a note in the scratchpad, and the work carries on. Ask about the collected suggestions together, each with its exact change, at the next point where my answer is needed anyway, or at the end of the task. That keeps the rule above without a stop for each one. The edit prompts still come when an agreed change is made. Suggestions still open at the end of a session go into the repository's handover, if it has a place for them.
- **Delete scratchpad files with `~/.claude/scripts/cleanScratch <path>…`,** not `rm`. It only deletes inside Claude's scratchpad, so `~/.claude/settings.json` allows it without a prompt.
- **Prune merged branches with `~/.claude/scripts/pruneMergedBranches [--dry-run]`,** not by matching branches to PRs by hand. It deletes only branches whose merged PR's last commit is the branch's tip (and their GitHub copy), so `~/.claude/settings.json` allows it.
- **Keep permission rules simple.** Before a complex one-off shell command (a `python3 -c` one-liner, a long pipeline, an inline script), check whether a dedicated tool or a simple command such as `jq` does the job. A one-off can't be allowed safely, so each one means a prompt or a rule that never matches again. When the same kind of command keeps coming back, propose a small script in the repository that checks its own input, with a narrow allow rule, rather than broad or one-off rules.
- **Check permission rule changes with `~/.claude/scripts/compareRules`,** rather than reasoning matches out by hand. Without arguments it lists the rules grouped by the settings files they're in (`~/.claude/settings.json`, and the repository's `.claude/settings.json` and `.claude/settings.local.json`); given commands, it shows what each file and all of them together decide (denied, asks, runs, default); `--file` compares other files, such as a draft of new rules. It imitates the documented matching (one simple command per line; it doesn't know the built-in read-only commands), so check a surprising result against the permissions docs.
- **Lighthouse from the command line** works for checking a page locally, within a few points of Chrome's DevTools on the deployed site (wedding101, 2026-10-10): `npx lighthouse@<version> <url> --only-categories=performance,accessibility,best-practices,seo --output=json --output-path=<scratchpad file> --chrome-flags="--headless=new --disable-features=AsyncDns"`, with `CHROME_PATH` set to Playwright's Chromium (under `~/Library/Caches/ms-playwright/`) when Chrome isn't installed. Pin a release that's at least two weeks old (`npm view lighthouse time --json`).
  - **Keep `--disable-features=AsyncDns` under Claude's sandbox.** Chrome's own DNS lookups don't get through it: requests to other hosts hang while `localhost` works, and the scores are then for the page's error state, which can still come out at 100.
  - **Check that it audited the intended page:** look at the final screenshot (`audits["final-screenshot"]`) and the status codes in `audits["network-requests"]`, not only the scores.
  - A page behind a login, such as Netlify's visitor protection, answers `401` to it. Run Lighthouse against a local build instead (`astro preview` or similar), or have the person run it in their own logged-in Chrome's DevTools.
